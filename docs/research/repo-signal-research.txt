I think there is a **really good idea here**, but there is one important GitHub limitation that actually makes the problem more interesting.

GitHub itself exposes repository traffic metrics such as **full clones, unique cloners, views, unique visitors, referrers and popular content**. However, the traffic API requires write access to the repository, and GitHub only exposes clone/view traffic for the **last 14 days**. ([GitHub Docs][1])

So I would frame your solution as:

> **A repository adoption dashboard that looks beyond stars and forks to understand whether people are actually discovering, using and adopting a project.**

### The interesting signals

I'd divide the dashboard into several dimensions rather than trying to create one magic "popularity score."

| Dimension                   | Signals                                                      |
| --------------------------- | ------------------------------------------------------------ |
| ⭐ **Recognition**           | Stars, star growth, watchers                                 |
| 🍴 **Propagation**          | Forks, fork growth                                           |
| 📥 **Acquisition**          | Clones, unique cloners                                       |
| 👀 **Interest**             | Views, unique visitors                                       |
| 🔨 **Development activity** | Commits, contributors, PRs                                   |
| 💬 **Community**            | Issues opened/closed, discussions, PR activity               |
| 🔗 **Discovery**            | Referrers, search/social/external traffic                    |
| 📦 **Usage**                | Releases, package downloads, container pulls where available |
| 📈 **Momentum**             | Change in each signal over time                              |
| 🕰️ **Retention**           | Repeat visitors/cloners where data allows                    |

And **clones are particularly interesting**.

Imagine:

> **1,200 stars / 8,500 unique cloners**

versus:

> **8,000 stars / 900 unique cloners**

Those repositories tell very different stories.

The first may have a relatively small visible GitHub community but substantial actual developer interest/use.

---

## I wouldn't call it a "GitHub analytics dashboard"

I'd make the concept slightly broader:

### **Repository Adoption Intelligence**

Something that answers:

> **"Is anyone actually using this thing?"**

rather than:

> "How popular is this repository?"

That distinction is important.

For example, your own projects are a perfect example. A project might have:

```text
Stars             23
Forks              4

But...

Unique visitors   740
Unique cloners    312
Clones            891
External referrals 127
Contributors       8
PRs                31
```

That tells you something that **23 stars doesn't**.

# There is a fascinating problem with clone data

This is where your idea gets technically interesting.

GitHub's clone endpoint gives you:

* total clones
* unique cloners
* daily/weekly breakdown

but only for the most recent **14 days**. ([GitHub Docs][2])

And importantly, GitHub describes these as **full clones, not fetches**. ([GitHub Docs][3])

So your application could become a **historical telemetry collector**.

For example:

```text
Day 1
  clones: 12
  unique: 8

Day 2
  clones: 17
  unique: 11

...

Day 14
  clones: 43
  unique: 31
```

Your service stores those observations.

Next day:

```text
Day 15
```

You collect the new 14-day window and persist it.

Over time you build:

```text
          GitHub
             │
             ▼
       ┌─────────────┐
       │ Collector   │
       └──────┬──────┘
              │
              ▼
       ┌─────────────┐
       │ Time-series │
       │   storage   │
       └──────┬──────┘
              │
              ▼
       ┌─────────────┐
       │ Adoption    │
       │   Engine    │
       └──────┬──────┘
              │
              ▼
       ┌─────────────┐
       │ Dashboard   │
       └─────────────┘
```

And suddenly you have something GitHub itself doesn't give the developer:

### **Historical repository adoption telemetry.**

---

# But there's a catch

This also means I **wouldn't initially build it as a public service where someone enters any GitHub URL.**

Because you won't be able to retrieve clone statistics for arbitrary public repositories.

GitHub's traffic APIs are available to people with **write access** to the repository. ([GitHub Docs][1])

Instead:

### MVP

User:

```text
Connect GitHub
      ↓
Select repositories
      ↓
Grant access
      ↓
Collector periodically retrieves metrics
      ↓
Dashboard
```

Then you can say:

> **Connect your GitHub account and start building your repository's adoption history.**

That's actually a compelling proposition.

# And I think there is a second phase

You could eventually have **two types of metrics**.

### GitHub-native

Collected from the repository owner:

```text
Stars
Forks
Clones
Unique cloners
Views
Unique visitors
Referrers
Popular pages
Commits
Contributors
Issues
PRs
Releases
```

GitHub's REST metrics APIs already provide repository traffic and repository activity data for these kinds of measurements. ([GitHub Docs][4])

### Ecosystem-native

Depending on the technology:

```text
npm downloads
NuGet downloads
PyPI downloads
Docker pulls
VS Code installs
Homebrew installs
Maven downloads
etc.
```

Then your dashboard starts answering a much more powerful question:

> **How is this project actually being consumed across the ecosystem?**

# One metric I'd definitely introduce

### **Stars → Usage divergence**

Not as a score, but as a visual indicator.

For example:

```text
              STARS          CLONES

Project A      ████████       █████████████████
Project B      █████████████  ███
```

And perhaps:

### "Usage signals are growing faster than recognition signals."

That could be extremely useful for open-source developers.

Because **stars are an intentional social action**.

A clone is much closer to:

> "I needed this code."

It still doesn't prove production usage — someone can clone a repo just to inspect it — but it is a materially different signal.

## I can see a really nice architecture for this

Given the kind of projects you've been building, I'd probably make this:

```text
                ┌──────────────────────┐
                │      GitHub App      │
                │ OAuth / permissions   │
                └──────────┬───────────┘
                           │
                           ▼
                 ┌───────────────────┐
                 │ Repository        │
                 │ Collector         │
                 └─────────┬─────────┘
                           │
             ┌─────────────┼──────────────┐
             ▼             ▼              ▼
        GitHub API     Package APIs    Other sources
             │             │              │
             └─────────────┼──────────────┘
                           ▼
                 ┌───────────────────┐
                 │ Adoption Data     │
                 │ Store             │
                 └─────────┬─────────┘
                           ▼
                 ┌───────────────────┐
                 │ Signal Engine     │
                 └─────────┬─────────┘
                           ▼
                 ┌───────────────────┐
                 │ Dashboard         │
                 └───────────────────┘
```

And I'd make the **raw observations immutable**:

```text
Repository
    │
    ├── Observation
    │     ├── timestamp
    │     ├── stars
    │     ├── forks
    │     ├── clones
    │     ├── unique_cloners
    │     ├── views
    │     └── unique_visitors
    │
    ├── Observation
    └── Observation
```

That gives you enormous flexibility later to derive new metrics without having to recollect historical data.

### A possible name

I wouldn't call it something generic like `GitHub Stats`.

The concept is more interesting than that.

Some directions:

* **RepoPulse**
* **Adopted**
* **RepoSignal**
* **OpenPulse**
* **RepoTelemetry**
* **RepoRadar**
* **ProjectPulse**
* **OpenSource Pulse**
* **RepoScope**
* **Adoption Radar**
* **CodePulse**
* **RepoBeacon**

I particularly like **RepoSignal** for what you're describing:

> **RepoSignal — understand how your open-source projects are actually being discovered, used and adopted.**

And there is a nice conceptual distinction:

**Stars tell you who liked it.
Forks tell you who copied it.
Clones tell you who got it.
Your telemetry tries to tell you what happened next.**

That feels like the core idea worth exploring.
